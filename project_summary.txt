================================================================================
                        SkyScanner Clone - PROJECT SUMMARY
================================================================================

1. PROJECT OVERVIEW
------------------
SkyScanner Clone is a state-of-the-art, premium web application designed for search,
comparison, and booking of airline flights. The application provides an elegant, 
high-end user experience (UX) characterized by a responsive multi-step checkout
funnel, interactive seat and boarding pass generations, and modern visual design 
cues (such as deep indigo glassmorphism gradients and smooth state transitions).

Under the hood, SkyScanner Clone supports both a fully functional real-time search mode 
powered by the SerpAPI Google Flights Engine and an advanced local mock system for
development and offline testing.


2. ARCHITECTURE & TECH STACK
----------------------------
The application is built on top of a modern frontend architecture:
* Core Framework: React 19 (declarative, component-driven UI structure)
* Build Tool & Dev Server: Vite (provides ultra-fast Hot Module Replacement - HMR)
* Styling System: Vanilla Tailwind CSS-compatible utility styles paired with custom 
  CSS variables for consistent premium branding.
* Icon Suite: Lucide React (vector-based iconography for a clean, consistent UI)
* API Client: Axios (manages structured AJAX/HTTP requests to flight services)


3. COMPONENT & FILE ARCHITECTURE
--------------------------------
The project's code files are organized inside a lightweight, highly modular structure:

* src/main.jsx
  - The main application entry point that mounts the root React component onto the DOM.

* src/App.jsx
  - The central coordinator of application state. It acts as a finite state machine
    tracking checkout stages ('search' -> 'outbound' -> 'return' -> 'review').
  - Orchestrates API triggers, stores selected flight cards, computes checkout totals, 
    and handles the logic for showing/hiding step progress and confirmation overlays.

* src/components/Header.jsx
  - Renders the brand identity banner, logo, and premium navigation links.

* src/components/SearchForm.jsx
  - The primary user entry panel. Collects departure airport, arrival airport, outbound 
    date, return date (if round trip), trip type (One Way vs Round Trip), and Cabin Class.
  - Implements customized styled selectors with One-Way as the active default option.

* src/components/FlightList.jsx
  - Receives flight search results from parent state. Loops through flight collections 
    and instantiates cards, handles loading indicators, and displays elegant "no flights 
    found" fallbacks.

* src/components/FlightCard.jsx
  - Represents individual flight segments. Parses flight duration minutes to clean 
    "Hours and Minutes" formats. Renders transit stop markers, airline logo, price labels 
    (with green "Included" tags for combined round-trip legs), aircraft information,
    CO2 emission statistics, and class-specific amenities.

* src/components/Footer.jsx
  - A clean, well-spaced premium footer containing copyright notices and useful links.

* src/services/flightService.js
  - The core API connector service. Contains the `searchFlights` async call which queries 
    `/api/search.json` via Axios.
  - Detects if `VITE_SERP_API_KEY` is present. If it is, the app communicates with the live 
    SerpAPI endpoint. Otherwise, it gracefully falls back to a highly dynamic local mock 
    generator.
  - Houses the `getClassDetails` helper which defines seat pitch (legroom), multiplier levels, 
    and customized amenities for each respective cabin class.


4. DETAILED FEATURE BREAKDOWN
-----------------------------
* Multi-Step Selection Flow:
  - Phase 1 (Search): User enters criteria in the search bar.
  - Phase 2 (Outbound selection): User views departing options, showing prices, airlines, 
    and specific amenities matching their chosen cabin class.
  - Phase 3 (Return selection - Round Trip only): Shows a sticky top banner summarizing the 
    user's departing choice, and renders returning options (where baseline prices are 
    represented as flight price differences).
  - Phase 4 (Review & Book): Displays a detailed split layout containing comprehensive itinerary 
    receipts (outbound and return side-by-side), individual route price breakdowns, 
    taxes, luggage allowances, and a "Price Lock Protected" secure badge.

* Digital Boarding Pass receipt:
  - Upon clicking "Confirm & Book", a modal overlay renders a custom digital ticket.
  - Shows passenger name, VP booking reference, assigned seat numbers, class details, 
    the total price paid, and a custom visual barcode.

* Cabin Class Customization:
  - Users can select Economy, Premium Economy, Business, or First Class.
  - Each class automatically updates details throughout the app:
    - Economy: 30 in legroom, Wi-Fi for a fee, In-seat power.
    - Premium Economy (1.5x price multiplier): 33 in legroom, Free Wi-Fi, Extra recline, Premium meal.
    - Business (3.0x price multiplier): 38 in legroom, Free high-speed Wi-Fi, Lie-flat seat, 
      Gourmet multi-course dining, Lounge access.
    - First Class (5.0x price multiplier): Private Suite, Lie-flat seat with bedding, Gourmet dining 
      on-demand, VIP Lounge access, Priority boarding.


5. API INTEGRATION & SERPAPI CONFIGURATION
------------------------------------------
To avoid CORS (Cross-Origin Resource Sharing) restrictions when connecting to external SerpAPI
servers directly from the client side during local development, the application utilizes a proxy 
inside `vite.config.js`:

```javascript
  server: {
    proxy: {
      '/api': {
        target: 'https://serpapi.com',
        changeOrigin: true,
        rewrite: (path) => path.replace(/^\/api/, ''),
      },
    },
  }
```

When a user searches for flights:
1. Axios sends a GET request to `/api/search.json`.
2. The Vite dev server intercepts this call and proxies it to `https://serpapi.com/search.json` 
   while preserving the request parameters.
3. The API request forwards crucial parameters, including `engine: 'google_flights'`, `departure_id`, 
   `arrival_id`, `outbound_date`, `return_date`, `type`, and `travel_class` (which maps values 
   '1', '2', '3', '4' to Economy, Premium Economy, Business, and First Class respectively).
4. The SerpAPI returns structured JSON results representing actual live flight listings.
5. If no API key is detected, the flight service falls back seamlessly to mock generators.

           PROJECT METHODOLOGY, PRD & ARCHITECTURE QUESTIONS

1. Problem Validation & Market Research:
Detailed Explanation:
- Problem Statement: Modern online flight booking platforms are often bloated with aggressive ads, hidden fees, confusing round-trip leg selection flows, and opaque cabin class pricing that only reveals true seat pitch or amenity costs at checkout.
- Target Market: Frequent flyers, leisure travelers, business professionals, and digital nomads seeking a streamlined, fast, visual, and transparent flight search experience.
- Market Analysis: Analyzed major flight aggregators (Google Flights, Skyscanner, Kayak). Identified three major user friction points: (1) lack of upfront visibility into cabin class perks (e.g., lie-flat seats vs standard recline), (2) confusing price calculations during return flight selection for round trips, and (3) slow, multi-page page reloads.
- Validation Outcome: SkyScanner Clone directly solves these issues by introducing a 4-step state machine checkout funnel, upfront cabin class selection (Economy, Premium Economy, Business, First), real-time pricing recalculations, clear return flight fare deltas, and instant digital boarding pass receipts.

2. Product Requirement Document (PRD):
Detailed Explanation:
- Core Objective: Build a high-performance, aesthetically premium React single-page flight search and booking application integrated with SerpAPI Google Flights Engine.
- Key Feature Requirements:
  1. Search Bar: Origin & Destination IATA code inputs, Outbound & Return date pickers, Trip Type radio toggle (One Way default, Round Trip option), Cabin Class dropdown (Economy, Premium Economy, Business, First Class).
  2. Multi-Step Funnel: Search -> Outbound Flight Selection -> Return Flight Selection (if Round Trip) -> Itinerary Review & Fare Summary -> Digital Boarding Pass Confirmation.
  3. Dynamic Cabin Class Engine: Update prices, seat pitch (legroom), and amenity tags (Wi-Fi, lie-flat seats, gourmet dining, lounge access) based on selected class.
  4. Dual Operation Modes: Production mode using SerpAPI Google Flights query API; Development mode using a realistic mock data fallback generator.
  5. Price Breakdown: Itemized fare calculations showing base ticket price, return flight adjustments, taxes/surcharges ($45), baggage inclusions, and a price lock guarantee.
- Non-Functional Requirements: Responsive across mobile/desktop, under 1-second render updates via Vite HMR, clean visual design with glassmorphism gradients and Lucide React icons.

3. User Stories & Acceptance Criteria:
Detailed Explanation:
- User Story 1 (Cabin Class Filtering): As a passenger, I want to choose my preferred cabin class (Economy, Premium Economy, Business, First) before searching so that I can see relevant prices and luxury amenities upfront.
  * Acceptance Criteria: Selecting a cabin class dynamically updates flight card pricing, displays exact legroom specs, and lists corresponding amenity tags (e.g., "Lie-flat seat", "VIP Lounge access").
- User Story 2 (Round Trip Selection Flow): As a round-trip traveler, I want to select my outbound flight first and then pick my return flight while keeping track of my departing choice.
  * Acceptance Criteria: Selecting an outbound flight advances the UI to the return leg step, shows a sticky top banner summarizing the chosen outbound flight details, and highlights returning flights with "+$X additional fare" or "Included" labels.
- User Story 3 (Review & Boarding Pass Confirmation): As a user finalizing a flight, I want to review an itemized price breakdown and receive a digital boarding pass receipt.
  * Acceptance Criteria: The Review screen displays outbound and return flight cards side-by-side, sums base fare + taxes, and opens a modal with passenger info, seat numbers, class, and barcode upon clicking "Confirm & Book".

4. Sprint Planning & Development Workflow:
Detailed Explanation:
- Agile Development Methodology: Iterative sprint planning focused on incremental feature delivery and immediate visual verification.
- Sprint Breakdown:
  * Sprint 1 (Foundation): Project scaffolding with Vite + React 19, setup Tailwind CSS styling system, created base Header, SearchForm, and FlightCard UI layout.
  * Sprint 2 (API Integration): Implemented `flightService.js` connecting to SerpAPI `/api/search.json` endpoint via Axios, added Vite dev server proxy to handle CORS, built local mock generator fallback.
  * Sprint 3 (State Machine Funnel): Implemented multi-step state management in `App.jsx` ('search' -> 'outbound' -> 'return' -> 'review'), connected flight selection callbacks across components.
  * Sprint 4 (UX Refinements & Polish): Added Cabin Class dropdown selector, updated form defaults (One Way left, Round Trip right), built dynamic pricing multipliers and amenity generators, and designed the Digital Boarding Pass modal.
- Workflow Tools: Git version control, component-driven development, live Vite HMR testing, and production build validation (`npm run build`).

5. System Architecture & Design Decisions:
Detailed Explanation:
- Single Page Application (SPA) Architecture: Built using React 19 and Vite for instant client-side rendering without full-page reloads.
- Centralized State Machine: Managed at the root in `App.jsx`, tracking current checkout step (`currentStep`), search parameters (`searchParams`), selected outbound/return flight objects (`selectedOutbound`, `selectedReturn`), loading indicators, and confirmation states (`isBookingConfirmed`).
- Key Design Decisions:
  * Vite Local Proxy (`vite.config.js`): Rewrites `/api` requests to `https://serpapi.com` during development, bypassing browser CORS (Cross-Origin Resource Sharing) restrictions cleanly.
  * Decoupled Flight Service Layer (`flightService.js`): Encapsulates API interactions and automatically switches between real SerpAPI Google Flights data and rich mock data based on `VITE_SERP_API_KEY` presence.
  * Aesthetic Design System: Custom color palette featuring deep indigo gradients (`bg-indigo-900`), glassmorphic panels, Lucide React iconography, rounded corners, and crisp typography.

6. Database Design (ER Diagram & Schema):
Detailed Explanation:
- Not Applicable.
- Reasoning: SkyScanner Clone is engineered as a client-side Single Page Application (SPA) that operates directly against external flight APIs (SerpAPI Google Flights Engine) and ephemeral React application state (`App.jsx`). It does not store user data, flight cache, or booking transactions in a database server (such as PostgreSQL, MySQL, or MongoDB).
- Future Extension Architecture (If Implemented): A full backend system would require an Entity-Relationship (ER) model with tables:
  * Users (id, email, password_hash, full_name, created_at)
  * Bookings (id, user_id, booking_ref, total_price, status, created_at)
  * Flights (id, flight_number, airline, departure_airport, arrival_airport, departure_time, arrival_time)
  * Tickets (id, booking_id, flight_id, seat_number, travel_class, price)

7. Swagger or postman:
Detailed Explanation:
- Not Applicable (for custom internal backend REST endpoints).
- Reasoning: SkyScanner Clone is a pure frontend application and does not host its own custom backend REST API server or Swagger UI / OpenAPI documentation endpoint.
- External API Specification: The application integrates with the external **SerpAPI Google Flights API**. During development, Postman was used to test and inspect SerpAPI request/response payloads for the endpoint `/api/search.json`. 
- Query Parameters Consumed:
  * `engine`: 'google_flights'
  * `departure_id`: Airport IATA code (e.g., 'SFO')
  * `arrival_id`: Airport IATA code (e.g., 'JFK')
  * `outbound_date`: YYYY-MM-DD
  * `return_date`: YYYY-MM-DD (optional for round trips)
  * `type`: '1' (Round Trip) or '2' (One Way)
  * `travel_class`: '1' (Economy), '2' (Premium Economy), '3' (Business), '4' (First Class)
  * `departure_token`: Passed during return flight queries to match chosen outbound leg.

8. Security Implementation (JWT, Hashing, RBAC):
Detailed Explanation:
- Not Applicable (for backend user authentication and authorization).
- Reasoning: SkyScanner Clone operates as an unauthenticated guest booking demonstration application without user login accounts, password hashing (e.g., bcrypt), JWT (JSON Web Tokens), or Role-Based Access Control (RBAC).
- Implemented Frontend & API Security Measures:
  1. Environment Variable Protection: Secret API keys (`VITE_SERP_API_KEY`) are isolated in `.env` files and accessed safely via `import.meta.env`, keeping credentials out of public source control repositories.
  2. CORS Mitigation & Proxy Shielding: API requests are routed through Vite's local dev server proxy, hiding raw target endpoints and adhering to browser security models.
  3. Client Input Sanitization: Form input fields enforce structured text formatting for airport codes and valid calendar dates before issuing queries.

9. Performance Optimization & Scalability:
Detailed Explanation:
- Code Splitting & Minification: Built using Vite and Rollup, generating optimized production bundles (`dist/assets/index-CamAyXwj.js` ~268 kB, `dist/assets/index-0X9sboeZ.css` ~24 kB) with tree-shaking enabled.
- Efficient DOM Rendering: React 19 virtual DOM diffing ensures minimal DOM updates during state changes. Conditional rendering ensures heavy components (like the Boarding Pass modal and Flight Lists) only mount when active.
- Asset & Icon Optimization: Replaced heavy bitmap graphics with lightweight vector icons from `lucide-react`. Airline logos are served directly from Google's high-availability CDN (`gstatic.com`).
- Scalability Strategy: Because SkyScanner Clone compiles to static HTML/CSS/JS assets, it can be deployed to global CDN edge networks (Vercel, Netlify, Cloudflare Pages, AWS S3 + CloudFront) capable of handling millions of concurrent user sessions with sub-100ms latency.

12. Business Model & KPI Metrics:
Detailed Explanation:
- Business Model: Online Travel Agency (OTA) Referral & Affiliate Monetization Model. SkyScanner Clone acts as a flight search aggregator, earning affiliate commissions on flight bookings, cabin class upsells (Premium Economy/Business/First Class upgrades), and ancillary services (Price Lock Protection, luggage add-ons).
- Key Performance Indicators (KPIs):
  1. Conversion Rate: Percentage of users who complete the 4-step search funnel to ticket booking confirmation.
  2. Average Order Value (AOV): Increased through upfront cabin class options (Business and First Class bookings yielding higher commissions).
  3. Search Response Time: Latency between search submission and flight card rendering (targeted under 1 second).
  4. Funnel Drop-off Rate: Percentage of round-trip users who exit between outbound flight selection and return flight selection.

13. Risk Analysis & Mitigation Plan:
Detailed Explanation:
- Risk 1 (API Rate Limits & Exhaustion):
  * Impact: External SerpAPI queries fail if monthly API quota is exceeded.
  * Mitigation: Built an inline local mock data generator in `flightService.js` that automatically serves realistic flight options when the API key is missing or encounters errors.
- Risk 2 (Network Failure / Timeout):
  * Impact: User experiences endless loading spinners or blank screens during flight search.
  * Mitigation: Implemented robust error catching with clear error alert banners and a single-click "Back to Search" button.
- Risk 3 (Fare Discrepancy Between Legs):
  * Impact: Round-trip return selection displays ambiguous or mismatched base fares.
  * Mitigation: Implemented explicit return flight price deltas (+$X / "Included") and locked total fares with a "Price Lock Protected" badge in the Fare Summary.

14. Challenges Faced & Solutions:
Detailed Explanation:
- Challenge 1 (Round-Trip Return Flight Flow & Fare Summing):
  * Problem: Originally, round-trip searches only displayed departing flights, and selecting a flight did not load returning options or update the fare total properly.
  * Solution: Re-engineered `App.jsx` into a multi-step state machine (`search` -> `outbound` -> `return` -> `review`), stored the outbound flight token (`departure_token`), triggered a return flight search query using that token, and updated the Fare Summary to compute `selectedOutbound.price + selectedReturn.price`.
- Challenge 2 (Cabin Class Dropdown & Dynamic Amenity Scaling):
  * Problem: Adding cabin class selection required dynamically updating prices, legroom pitch, and amenity tags across both live SerpAPI queries and offline mock generators.
  * Solution: Added `travel_class` state to `SearchForm.jsx`, updated `flightService.js` to accept `travel_class` ('1' to '4'), built the `getClassDetails` helper to scale prices (1.0x to 5.0x) and generate class-specific amenities (Lie-flat seat, Lounge access, Private suite), and forwarded `travel_class` in both outbound and return API calls.
